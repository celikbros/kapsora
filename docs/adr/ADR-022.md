# ADR-022: KAPSORA authenticates its own users; no external identity provider in the MVP

- Status: Accepted — supersedes ADR-005 (Keycloak OIDC and BFF session)
- Date: 2026-09-03
- Deciders: Business owner (scope), Claude (design)

## Context

ADR-005 and v1.2 section 18.1 chose Keycloak as the identity provider. That choice rested on
one requirement: a corporate customer would want to sign in with its own directory (Active
Directory / Entra ID) through OIDC or SAML federation, plus the MFA, password policy and
account lockout that come with a mature IdP.

On 2026-09-03 the business owner removed that requirement: *"Bankanın Active Directory'si ile
işimiz yok. Bu bağımsız çalışan bir sistem."* KAPSORA manages its own users.

What Keycloak still costs when nobody federates through it:

- a second runtime (a JVM) beside the Go binaries, in a deployment model that has just been
  made container-free (ADR-021), on developer machines that have no JDK;
- its own database, its own upgrade and CVE cycle, its own realm configuration to keep in
  sync with the application's roles;
- a redirect-based login whose screens are Keycloak's, not the product's, so branding and
  Turkish wording are a theming exercise.

What it would still have given us: password storage, MFA, password reset and lockout. Those
are the pieces we now own.

The sibling projects in this codebase (`bioexamine`) already authenticate their own users
with Argon2id and an opaque session whose digest is what the database stores. Matching that
pattern keeps one security model across the group instead of two.

## Decision

KAPSORA authenticates its own users.

1. **Credentials.** `iam.credential` holds an Argon2id hash in PHC encoding, with the OWASP
   baseline parameters (19 MiB, 2 iterations, 1 lane). The parameters travel inside the hash,
   so raising them later re-hashes on next login instead of locking anyone out. A login-capable
   actor is an `iam.actor` row with `identity_issuer = 'kapsora'` and `identity_subject` = the
   normalised user name, so the existing unique constraint enforces user-name uniqueness and a
   federated issuer can be added beside it later without a data migration.
2. **Sessions.** `iam.session` stores the SHA-256 hash of an opaque 32-byte session id. The
   browser holds the id in an `HttpOnly`, `Secure`, `SameSite=Lax`, `__Host-` prefixed cookie
   and nothing else. Idle timeout 30 minutes, absolute lifetime 8 hours, both configurable.
3. **CSRF.** The token is derived as `HMAC-SHA256(cookie signing key, session id)` and returned
   by `GET /api/v1/session`. It is not stored: it rotates with the session and adds no column.
4. **Brute force.** Two independent layers: a per-address rate limit in front of the login
   endpoint, and a per-account lockout (10 consecutive failures, 15 minutes) applied in a single
   atomic `UPDATE` so parallel attempts cannot overshoot the threshold.
5. **Enumeration.** An unknown user name and a wrong password return the same problem body and
   take the same time; the unknown-user path deliberately performs a dummy Argon2id verification.
6. **Step-up.** Sensitive operations re-verify the password and open a 10-minute window.
7. **No OAuth tokens exist anywhere** — not in the browser, not in the database.

## Consequences

- One less runtime to install, operate, patch and back up; the login page is ours, in Turkish.
- We own password reset (needs the notification module, so it arrives with M4), MFA (TOTP is a
  later increment) and any future SSO.
- **If a customer later demands SSO**, it is added as a *second* login method: a new
  `identity_issuer` and an OIDC adapter behind the same session layer. Sessions, CSRF, step-up
  and every consumer of `identity.RequestContext` stay unchanged, so this is an addition and not
  a rewrite. That is the reason the actor table keeps an issuer column at all.
- MFA is not available in M1. For the pilot this is accepted; it must be revisited before any
  deployment that handles production health data (v1.2 section 18.1 lists MFA as required, and
  that requirement is deferred, not cancelled).
- v1.2 sections 15.3 and 18.1, and ADR-005, are read through this ADR. The frozen v1.2 text is
  not edited.
